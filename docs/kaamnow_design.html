KaamNow

A phone-first marketplace that connects rural and small-town workers in India — masons, farm labour, plumbers, helpers — to nearby customers who need them. Built for low-literacy users, with WhatsApp at its heart.

Phone-first OTP auth WhatsApp-native UX FastAPI + React + MongoDB Bilingual (Hindi / English)

01 Executive Summary

What KaamNow does

KaamNow is a two-sided marketplace that helps people in India's villages and small towns find local work, and helps small employers (families, farmers, shopkeepers, contractors) find reliable workers nearby. A customer can post a job — "need 4 people for cotton harvesting on Friday" — and workers in the area get matched, can express interest, and the customer picks who to hire.

The problem we solve

  • For workers: Daily-wage work in rural India is found through word-of-mouth and middlemen who skim earnings. Workers have no way to advertise their skills or rates beyond their village.
  • For customers: Finding even one trustworthy mason, electrician, or farmhand can take days of asking around. There is no visibility into who is available, what they charge, or their reputation.
  • For both: Most existing apps assume smartphones, good internet, email addresses, and basic English literacy — none of which can be assumed in our target market.

Target users

Workers

Blue-collar service providers in semi-urban and rural India — construction labour, farm workers, drivers, domestic help, tradespeople. Often low-literacy. Mobile-only (mostly entry-level Android, some feature phones).

Customers

Small employers in the same areas — farmers needing harvest help, families needing a plumber, small contractors needing crew. They are not businesses with procurement teams; they are individuals making one-off hires.

High-level technical summary

KaamNow is a web and mobile application powered by a Python (FastAPI) backend and a MongoDB Atlas database. The entire authentication system is phone-number based — no email is ever collected. We use WhatsApp (via Gupshup) both as a notification channel and as a parallel access path for users who prefer chat over a web app. The product is built and ready to deploy on Oracle Cloud (Kubernetes), and runs locally for development without paid third-party services.

How the pieces fit together

  • End users are customers, workers and admins. They never talk to the database directly — they always go through one of the client apps.
  • Client apps are the web app, the mobile app, and the WhatsApp bot. The web and mobile apps are visual; the WhatsApp bot is a text-message conversation. All three talk to the same backend.
  • Backend (FastAPI) is the brain. It validates every request, runs the business rules (who can book whom, when, for what price), and reads/writes the database. It is organised into logical modules — Auth, Marketplace Core, Admin, Notifications, WhatsApp Webhook — but it is a single deployed service.
  • MongoDB Atlas is the single source of truth: every user, job, booking and message log lives here.
  • Third-party services handle the things we deliberately don't build ourselves: Gupshup sends WhatsApp messages; MSG91/Exotel will send SMS OTPs in production (currently mocked for development); a public Indian Postal API auto-fills address fields from pincode.

03 Database & Entity Relationships

We use MongoDB, which stores data as flexible JSON-like documents rather than rigid tables. Each "collection" below is what a traditional database would call a table.

Main collections

How the entities connect — in plain English

  • A user is the basic account. Every account has a phone number and a role: customer, worker, or admin.
  • If the user is a worker, they have one extra worker profile record holding their skills, rate, and location.
  • A customer can post any number of jobs.
  • When a worker expresses interest in a job, an engagement record is created. This is the matchmaking thread — it tracks "requested", "accepted", "rejected", "cancelled" or "completed".
  • When the customer accepts an engagement, it converts into a booking — the formal hire record, where ratings and reviews eventually attach.
  • Every state change (interest received, booking accepted, booking cancelled) creates a notification for the relevant user, and optionally fires a WhatsApp message logged in wa_notif_log so we never spam the same person twice.
  • OTPs are short-lived rows used only during phone login; they self-expire.

04 Component Breakdown

Each major capability of the product is a self-contained module on the backend, with matching pages on the frontend. Below is each one.

4.1 — Authentication (Phone + OTP)

Purpose: Sign users up and let them log in using only their mobile number. No email, no password mandatory.

Key files

  • backend/routers/auth.py — the three-step OTP API
  • backend/auth.py — JWT and temporary-token utilities
  • backend/otp_service.py — multi-channel delivery (WhatsApp → SMS → Voice)
  • frontend/src/contexts/AuthContext.jsx — client-side OTP flow state
  • frontend/src/pages/PhoneSignup.jsx, frontend/src/pages/Login.jsx
Figure 4.1 — OTP signup sequence
sequenceDiagram autonumber participant U as User (phone) participant FE as Web/Mobile App participant API as Backend participant DB as MongoDB participant WA as Gupshup (WhatsApp) U->>FE: Enter mobile number FE->>API: POST /auth/send-otp API->>DB: Save OTP + expiry API->>WA: Deliver code (with SMS fallback) WA-->>U: "Your KaamNow code: 1234" U->>FE: Type code FE->>API: POST /auth/verify-otp API->>DB: Match code, check attempts API-->>FE: temporary signup token alt New user FE->>API: POST /auth/signup-complete (name, role) API->>DB: Create user with phone_primary API-->>FE: Auth token + profile else Existing user FE->>API: POST /auth/login-complete API-->>FE: Auth token + profile end

Step by step

  1. User types their phone number and asks for a code.
  2. The backend generates a 6-digit code, stores it with a short expiry, and asks Gupshup to deliver it via WhatsApp (falling back to SMS later).
  3. The user types the code into the app.
  4. The backend checks it matches and isn't expired, and returns a short-lived "signup token".
  5. If this phone is new, the app asks for a name and role (worker or customer) and creates the account. If the phone already exists, it logs them in directly.

External integration: Gupshup (WhatsApp). MSG91 and Exotel are wired in as fallbacks but currently mocked for development.

4.2 — Onboarding (Customer & Worker)

Purpose: Collect just enough profile information to make matchmaking work — without overwhelming a low-literacy user.

Key files

  • frontend/src/pages/CustomerOnboarding.jsx — pincode + village location
  • frontend/src/pages/WorkerOnboarding.jsx — name, address, skills, daily rate, photo
  • frontend/src/lib/usePincode.js — auto-fills district/state/block from Indian Post API
  • backend/routers/auth.py (PATCH /auth/me) — saves profile changes

The user types only their pincode and village name; district, state, post office, and block fill in automatically. This was a deliberate choice: rural users know their village name but rarely know their administrative block.

4.3 — Marketplace (Workers + Jobs)

Purpose: Let customers search for workers and let workers see relevant jobs.

Key files

  • backend/routers/workers.py — worker search, profile photo upload, availability toggle
  • backend/routers/jobs.py — job posting and feed
  • frontend/src/pages/Marketplace.jsx — worker grid (customer view)
  • frontend/src/pages/PostJob.jsx — job posting form
  • frontend/src/pages/WorkerJobFeed.jsx — nearby jobs (worker view)
Figure 4.3 — Job posting flow
flowchart LR A["Customer fills form
title · category · date · pay"] --> B["POST /jobs"] B --> C{"Validate fields"} C -->|ok| D["Save to jobs collection"] D --> E["Find matching workers
(skills + nearby pincode)"] E --> F["WhatsApp alert to each

Step by step

  1. The customer fills out a short job form (title, category, daily rate, date, pincode).
  2. The backend stores the job and immediately looks up workers whose skills and area match.
  3. A WhatsApp alert goes out to those workers. The deduplication log makes sure no worker receives the same alert twice.
  4. Workers see the job appear in their feed and can express interest with one tap.

4.4 — Engagement (Match → Hire)

Purpose: The actual matchmaking — worker expresses interest, customer accepts or rejects, hire is locked in.

Key files

  • backend/engagements.py — core state machine (request, accept, reject, cancel, complete)
  • backend/routers/engagements.py — HTTP endpoints
  • frontend/src/pages/Dashboard.jsx — customer's "interested workers" list
  • frontend/src/pages/WorkerDashboard.jsx — worker's active engagements
Figure 4.4 — Engagement state machine
stateDiagram-v2 [*] --> Requested: Worker taps "Interested" Requested --> Accepted: Customer accepts Requested --> Rejected: Customer declines Requested --> Cancelled: Worker withdraws Accepted --> Completed: Job done & rated Accepted --> Cancelled: Either party cancels Rejected --> [*] Cancelled --> [*] Completed --> [*]

When an engagement moves to Accepted, the system unlocks contact details (phone numbers) for both sides, fills the job's accepted-worker count, and marks the job as booked once it is fully staffed. Every state change writes a notification and, where relevant, a WhatsApp message.

4.5 — WhatsApp Bot & Notifications

Purpose: Let users who cannot or will not use the app still find work or workers — entirely inside WhatsApp.

Key files

  • backend/routers/whatsapp.py — webhook handler + conversational bot
  • backend/whatsapp_notify.py — outbound message helper

Gupshup forwards every incoming WhatsApp message to our webhook. The backend identifies the user by their phone number, looks up where they are in the conversation (stored in bot_sessions), and replies with the next step — show workers, confirm a booking, give a number to call. New users who message the bot are auto-created as guest customers without ever opening the app.

4.6 — Admin Panel

Purpose: Internal tool for the founding team to inspect users, jobs, and platform health.

Key files

  • backend/routers/admin.py — protected admin endpoints (user list, edit, deactivate)
  • frontend/src/pages/AdminDashboard.jsx — admin UI
  • backend/routers/stats.py — aggregate counts shown on the landing page

The admin role is granted only to the seeded admin account. From the admin panel, the team can search users, change their role, deactivate problematic accounts, and see live counts of jobs, workers, and bookings.

05 End-to-End User Journey

To show how all the parts come together, here is the most important complete flow: a customer posts a job and successfully hires a worker.

Figure 5.1 — Post job → hire worker (end to end)
sequenceDiagram autonumber participant C as Customer participant W as Worker participant FE as Web App participant API as Backend (FastAPI) participant DB as MongoDB participant WA as WhatsApp (Gupshup) C->>FE: Open app, tap "Sign up" FE->>API: Phone OTP flow (send → verify → signup-complete) API->>DB: Create user (role=customer) C->>FE: Fill village + pincode (auto-fills district/state) FE->>API: PATCH /auth/me API->>DB: Save address on user C->>FE: Post job (title, date, rate, pincode) FE->>API: POST /jobs API->>DB: Insert job (status=open) API->>DB: Find nearby workers matching skills API->>WA: Notify each matched worker WA-->>W: "New job near you: ..." W->>FE: Open feed, tap "I'm interested" FE->>API: POST /engagements API->>DB: Insert engagement (status=requested) API->>DB: Write notification for customer C->>FE: See interested workers, accept one FE->>API: POST /engagements/{id}/accept API->>DB: Engagement → accepted, job.filled_count +1 API->>DB: Mark job booked if fully staffed API->>WA: Send contact details to worker WA-->>W: "Accepted! Customer phone: ..." Note over C,W: Both parties have phone numbers,
job happens offline W->>FE: After job: mark complete C->>FE: Rate the worker FE->>API: POST /bookings/{id}/rate API->>DB: Update worker.avg_rating, total_jobs

Narrative walkthrough

  1. Sign-up: The customer downloads the app and signs in with their mobile number using a one-time code. No email, no password.
  2. Profile: They enter their village and pincode. The system fills in district, state, post office and block automatically.
  3. Posting: They post a job — say, "Need a mason for boundary wall, ₹500/day, starting Monday in Pratapgarh."
  4. Matching: The backend finds workers who (a) have masonry as a skill and (b) are in or near that pincode, and sends each one a WhatsApp message.
  5. Interest: A worker taps "Interested" in the app. An engagement is created in the database, and the customer sees them appear in their dashboard.
  6. Hire: The customer accepts one of the interested workers. Both phone numbers are now shared with each other so they can coordinate offline. The job is marked as booked.
  7. Work happens offline: The worker shows up; the customer pays cash on the day. KaamNow currently does not handle payments.
  8. Closeout: When the work is done, both parties confirm completion and the customer rates the worker. The worker's average rating and job count update.

This entire flow can also happen without the app: the customer can send "Hi" on WhatsApp and the same bot will walk them through booking a worker.

06 Technology Stack & Rationale

LayerTechnologyWhy this choice
Web frontendReact 18 + Tailwind CSS + Radix UIFast to build, huge talent pool, and the largest ecosystem of accessible UI components — accessibility matters when our users have low literacy.
Mobile appReact Native (Expo)One codebase for iOS and Android, and Expo lets non-technical testers install pre-release builds on their phones without app-store review.
BackendPython 3.12 + FastAPIModern, async, very fast to ship; FastAPI's built-in input validation cuts a class of bugs before they hit production.
DatabaseMongoDB Atlas (cloud)Document model fits flexible user profiles (workers, customers, admins have overlapping but different fields); Atlas handles backups and scale-out for us.
AuthPhone-only JWT + OTPEmail is irrelevant to our users. Phone numbers are universal in our target market and tie naturally to WhatsApp.
MessagingGupshup (WhatsApp Business)India's leading WhatsApp BSP; supports template messages, two-way conversation, and bulk notifications at low per-message cost.
OTP fallbacksMSG91 (SMS), Exotel (Voice)Built into the OTP service as fallbacks for users whose WhatsApp delivery fails — important for feature-phone-only users.
Pincode lookupapi.postalpincode.in (India Post)Free, official, and removes a major source of data-entry errors during onboarding.
HostingOracle Cloud Kubernetes (planned)Oracle's free tier gives a real production VM at zero cost during early stages; Kubernetes is the industry standard once we scale.
Reverse proxy / TLSNGINX Ingress + cert-managerFree TLS via Let's Encrypt; the same pattern used by virtually every modern Kubernetes deployment.
TestsPytest + custom DummyDbTests run without a real MongoDB instance, so any developer can clone the repo and run the whole suite in seconds.

07 Current Implementation Status

Based on the code in the repository today, here is what's done, what's partially done, and what is still ahead.

Fully built

  • Done   Phone-first OTP signup and login (both web and mobile)
  • Done   Worker and customer onboarding with pincode-based address autofill (including Block / Tehsil)
  • Done   Worker search and worker profile pages, with photo upload
  • Done   Job posting and the worker job feed
  • Done   Engagement state machine (interest → accept → complete), including contact-detail sharing on accept
  • Done   Notifications (in-app) and WhatsApp message dispatch with deduplication
  • Done   Admin dashboard (user list, role edit, deactivate)
  • Done   WhatsApp conversational bot — full booking flow without opening the app
  • Done   Bilingual UI (Hindi / English)
  • Done   Kubernetes deployment manifests and one-command deploy script for Oracle Cloud
  • Done   Comprehensive backend test suite using an in-process MongoDB stand-in

Partially built

  • Partial   OTP delivery — the multi-channel service (WhatsApp → SMS → Voice) is fully implemented but MSG91, Exotel and Voice providers are mocked. Real keys need to be plugged in for production.
  • Partial   Mobile app — mirrors the web app's core flows but has not been hardened against feature-phone constraints (memory, intermittent network).
  • Partial   Ratings & reviews — the booking model supports ratings and the worker profile shows average rating, but the end-to-end "rate after completion" UX is minimal.
  • Partial   Waitlist — backend endpoint and landing-page form work, but there is no admin export of the list yet.

Not yet started

  • Todo   Payments — KaamNow currently does not collect or move money. The product plan calls for a ₹30 per-booking fee from customers, which will need a payments provider (Razorpay or similar).
  • Todo   Trust & verification tiers — the worker schema reserves a trust_tier field, but the verification process (SHG vouching, ID upload) is not yet implemented.
  • Todo   Dispute resolution — there is no formal "report a worker / customer" or chargeback flow.
  • Todo   Analytics & growth instrumentation — no event pipeline yet; the admin stats endpoint shows totals but not funnel data.
  • Todo   SMS-only feature-phone path — designed in the redesign plan, partially scaffolded, but the full IVR / SMS-based booking flow is not built.
